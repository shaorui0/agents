c0003 report-verify

What changed

  • tools/verify.py: exit-code gate for a triage report.md. S1 required sections, E1/E2 evidence chain (every conclusion cites [E<n>], every id defined in the log), E3 evidence has timestamp and query, A1/A2 Slack reply has no over-assertion and hedges, O1/O2 every mutating command has # INTENT: and awaits approval. Exit 0 PASS, 1 WARN, 2 FAIL.
  • fixtures/report_ok.md and fixtures/report_bad.md: synthetic reports; ok exits 0, bad exits 2 and names every defect class.
  • tests/test_verify.py: 11 tests, including single-edit mutations of the ok fixture.
  • README reorganized: one line, Quickstart, How I think (8 rows), layout, Progress, License.

Why

“Evidence-backed” and “no over-assertion” were prompt advice. An exit code turns each real oncall into an eval run, and a pass-rate over reports shows whether the skill is decaying.

Design decisions

  • The verifier reuses the Gate 3 classifier to decide which commands are mutating. A second regex list in verify.py would drift from the gate; one source means a command the gate would block is a command that needs INTENT.
  • Three levels. FAIL blocks sending. WARN means review. Missing timestamp is a warning, a dangling evidence id is a failure: the first is sloppy, the second is a conclusion with no support.
  • Mutation-style tests. Instead of many fixtures, each test edits one thing in the ok fixture and asserts the specific code reacts. Failures point at the check that broke.

Result

48 tests green in total; make verify passes (ok gives 0, bad gives 2). The README Quickstart commands were run and their output is in the evidence.
